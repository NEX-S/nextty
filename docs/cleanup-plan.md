# nextty 整洁计划

依据提交 `31c3125`（2026-11-19）的代码审计、实测基线和 CPU 剖析。目标：用最少的进程、线程、类型和代码完成现有功能，做到现代、高性能、低输入延迟、轻量。前端、守护进程、桥接和 Agent 所有者始终来自同一次构建，所以内部协议、磁盘历史格式和进程接口不保留任何兼容层。用户可见的功能、按键和配置项保持不变；第 8 节的取舍须经确认才执行。

这些线程用了 11 种自建的“线程 + 队列 + 唤醒”实现：`terminal-io`、历史、历史搜索、`worker::Worker`、`ClipboardReader`、`ClipboardReceiver`、资源采样、Agent 对话、跟踪写入、C 渲染、C 剪贴板发送。每个窗格有 2 个常驻线程（搜索线程首次使用后也常驻，共 3 个）、4 把锁、5 个通道、4 个 eventfd。按键回显一次要经过 7 次唤醒：前端 →（套接字）→ 守护进程主循环 → PTY → 子进程 → PTY → `terminal-io` 解析 →（eventfd）→ 主循环取帧 →（套接字）→ 前端。

### 2.3 主要问题

1. **并发结构比需求重。** 守护进程在持有该窗格 Core 锁时写入按键（`workspace.rs:2646`），按键要排在 I/O 线程正在做的解析之后。11 种后台线程实现各自处理唤醒、关闭和错误。
2. **同一事实存多份。** Agent 转写文本在所有者、守护进程和每个前端各存一份，回复在 Markdown 缓存里还有一份；草稿和附件在前端和守护进程的 JSON 里各存一份；守护进程为每个连接另存一份进程元数据，只为做差。
3. **同一消息多种表示。** 除 `Action`/`Response` 外，还有逐项转发的 `ClientEvent`（`workspace.rs:503-543, 868-902`）。Agent 的草稿、请求、恢复状态和启动参数是嵌在二进制协议里的 JSON。27 个手写编解码函数（`wire.rs:1246-2275`，1,030 行）成对维护。版本号有三套：帧头字节、套接字文件名、桥接参数与握手。
4. **同一功能两份实现。**
   - GUI 和 TUI 各自实现布局、命中测试、鼠标、关闭确认、标签栏和监控器绘制，约 1,000 行重复，行为已经出现分歧（附录 A）。
   - Core 带一套只在测试中、或磁盘写入失败后才会走的内存历史（`core.rs` 中 27 处分支）。
   - 有三个单行编辑器，“行拼接为文本”写了四遍。
5. **历史子系统机制过多。** 冷历史异步重排、按序号维护的段预算、逐窗格的淘汰通知、守护进程里三个重试队列（复制、读取、搜索），以及三套各自实现的归档遍历。
6. **热路径上有浪费。**
   - 磁盘历史模式下，每滚出一行都 `malloc` 一个新行，再由历史线程跨线程释放。剖析显示这约占瓶颈线程四分之一的时间，吞吐比内存路径低 25%。
   - 每次滚动都标记整屏为脏。
   - 每帧都要锁定几乎所有窗格，并对没有 OSC 7 的窗格执行 `readlink`。
   - Agent 编辑框每按一次键，就序列化并广播所有会话的草稿和附件。
   - 每完成一次工具调用，就重发整个转写文本。
   - TUI 每帧都整块重发侧栏、预览和弹窗。
7. **防御代码和开发脚手架进入了产品。** 永远不会触发的校验、事件队列和 SSE 的尺寸上限、产品二进制里的跟踪线程，以及把 `io::Error` 再包一层的 `error.rs`。
8. **构建分支和测试。** 85 处特性门控中有 66 处只为区分“有没有 TUI”。约 6,500 行测试直接驱动内部结构、钉死实现中的具体数值或枚举边界输入（第 6 节）。`examples/bench` 测的是生产从不运行的无历史路径。

## 3. 改造原则

1. **一个事实一个来源。** 每份状态只有一个所有者；其他地方要么借用，要么接收增量，不保存第二份副本再比较。
2. **一种机制做一件事。** 一次性后台任务只有一种实现，“只保留最新请求”的任务只有一种实现；大块数据只有一种分块传法；每个方向只有一个消息枚举。
3. **线程只为阻塞或可测的并行而存在。** 新线程必须对应会阻塞事件循环的工作（磁盘、网络、子进程等待），或经测量能提速的 CPU 工作（字形塑形与栅格化）。每个线程一个所有者、一个输入队列、一条结果通道。
4. **异步 = 非阻塞 fd + 每个进程一个 `poll` 循环。** 不引入通用异步运行时；阻塞工作交给第 3 条允许的线程。
5. **同构建，无兼容。** 只保留一个版本常量，用于在握手时拒绝不同的构建；不做字段级兼容、旧格式迁移或可选字段协商。
6. **只在会损坏数据的地方校验。** 删除只拒绝“正确使用时不会出现”的输入的检查。协议解码保留帧长上限，防止损坏的帧引发巨量分配。
7. **测试保护难以肉眼发现的行为。** 保留录制回放、协议分帧、真实 PTY/守护进程/历史的集成测试；删除复述实现或枚举边界的测试。
8. **性能改动以测量为准。** 每个批次前后都跑第 9 节的测量，劣化即回退该改动。

## 4. 目标架构

### 4.1 进程：角色不变，接口收窄

| 进程 | 存在理由 | 目标形态 |
|---|---|---|
| 前端 `nextty [--gui\|--tui]` | 呈现与交互 | 一个 `poll` 循环；GUI 另有渲染线程 |
| 守护进程 `--server` | 持有 PTY；分离与重连；多个查看端 | 单线程反应器 + 历史写线程 + 一次性任务线程 |
| Agent 所有者 `--agent-owner` | 前端分离后对话继续；凭据只在本机 | 主循环 + 每个对话一个模型线程；消息类型化 |
| 远程桥接 `--bridge` | OpenSSH 只提供字节流 | 启动并连接远端守护进程后，只做字节转发 |

### 4.2 线程

| 进程 | 线程 |
|---|---|
| 守护进程 | **反应器**：负责监听套接字、客户端、所有 PTY 和 pidfd、定时器；解析、取帧和处理动作都在这里完成，`Core` 不加锁。**历史写线程**：负责所有窗格的段写入、共享预算淘汰和冷页读取；用完的行缓冲还给反应器复用。**一次性任务线程**：历史搜索、读取、复制导出、Agent 文件操作和进程元数据采样，每个请求一个，带取消标志，结果进入反应器唯一的结果队列和 eventfd。 |
| 前端 | UI 线程或主线程；GUI 的 C 渲染线程；`worker::Worker`（只保留最新请求）负责文件扫描、文件预览、Markdown 排版和每秒一次的资源采样。 |
| Agent 所有者 | 主循环；每个对话一个模型线程。 |
| 桥接 | 单线程。 |

自建后台线程机制从 11 种减到 5 种：`Worker`、一次性任务、历史写线程、Agent 对话线程、C 渲染线程。

删除的线程：`terminal-io`、历史搜索线程、`ClipboardReceiver`、`ClipboardReader`、资源采样线程、跟踪写入线程和 C 剪贴板发送线程，连同它们各自的锁、条件变量和 eventfd。

**为什么守护进程用单线程反应器：**
- **两种布局都有低延迟的成熟实现。** kitty（一个 I/O 线程轮询全部子进程，主线程解析）、foot（读取和解析都在主循环）和 tmux 用一个循环处理所有 PTY；Alacritty、Ghostty、WezTerm 每个终端一到两个线程，靠锁与渲染交接（来源见第 10 节）。
- **延迟差异主要不来自线程布局。** 公开测量显示，差异主要来自刻意的输入/重绘延迟、垂直同步与合成器（[LWN 2018](https://lwn.net/Articles/751763/) 测得 Mutter 至少增加 8 ms），以及等锁时间。所以选择单线程反应器的理由是简单：删掉 Core 锁、按键写入时的等锁、每个窗格的唤醒 fd 和通道，并在回显路径上少一次跨线程唤醒。延迟只要求不劣化。
- **窗格之间并行解析在这里没有收益。** 单核纯解析可达 400 MiB/s，经 PTY 的生产路径为 111–149 MiB/s，远超前端能显示的量。
- **公平性靠预算，阻塞工作留在线程里。** 每个窗格每轮有解析预算，输入先于输出处理；磁盘、遍历和网络工作仍留在线程里，因为它们会阻塞。

### 4.3 关键路径

- **按键：** 前端 →（套接字）→ 反应器 → 非阻塞 `write` 到 PTY。全程不持锁；写不完的字节进入该窗格的队列，等 `POLLOUT`。
- **回显：** PTY 可读 → 反应器读取并解析 → 若有连接持有待处理的帧请求，同一轮内取帧并发送 → 前端。唤醒次数从 7 次降到 6 次。
- **帧：** 每个连接记录自己收到的最后版本，只接收对它而言变化了的行；工作区快照只在变化时发送；后台标签页只计算元数据。
- **历史：** 滚出的行连同缓冲一起交给历史写线程，编码后缓冲回收。预算淘汰的结果经结果队列告知反应器。复制、搜索和读取由一次性任务直接读取已写好的段文件，不占用写线程。
- **GUI 帧节奏：** 保持现状：空闲后首帧立即提交，连续输出时按刷新率封顶，一个待处理绘制包，一个在途帧。只有测量证明有收益时才调整。

### 4.4 协议

- 每个方向一个消息枚举：`Action`（前端或所有者 → 守护进程），`Response`（守护进程 → 前端或所有者）。前端直接匹配 `Response`。
- 编解码由 `serde` derive 生成，二进制格式用 postcard 1.x（`default-features = false, features = ["alloc"]`；1.0 起线格式有文档且稳定）。直接依赖从 6 个变为 8 个（加 `serde` 的 `derive` 特性和 `postcard`）。新增的都是编译期 crate：`serde_derive`、`syn`、`quote`、`proc-macro2`、`unicode-ident`（已在 `Cargo.lock` 中，只是目前未编译），以及 `postcard`、`cobs`、`thiserror`、`thiserror-impl`。冷构建实测从 23.46 s 增至 25.20 s（批次 2，全新 target 目录），运行时没有额外开销。
- postcard 对 `Vec<u8>` 逐字节编码，所以 PTY 输入、剪贴板块等字节字段使用一个调用 `serialize_bytes` 的 `Bytes` 新类型。屏幕行保留现有的紧凑编码（文本段 + 样式段），因为 SSH 带宽在意它；行编码实现为该类型的手写序列化。
- 版本：套接字文件名继续带版本号，用来隔离本机的不同构建；SSH 握手只交换一个 `wire::VERSION`；每帧不再携带版本字节。
- 大块数据只有一种传法：分块流式传输，本地和 SSH 相同。删除 `SCM_RIGHTS` 文件描述符传递和两个剪贴板线程。
- Agent 的草稿、请求、恢复状态和启动参数改为类型化结构体，二进制帧里不再嵌 JSON。

### 4.6 保持不变的部分

以下部分已经符合目标，本计划不改动：
- **平台机制：** pidfd、eventfd、`O_TMPFILE`；Vulkan 1.3 动态渲染与 mailbox 呈现；`wp_presentation`、fractional-scale、text-input-v3；Rust edition 2024。
- **终端核心：** 16 字节单元格和稀疏附加数据、VT 解析器、Shell 集成标记。
- **渲染：** C 渲染管线（一个待处理绘制包、一个在途帧、按需增长的字形图集）。
- **系统库：** 字体、塑形、栅格化、HTTP 与 TLS 继续用系统库。
- **Agent：** `docs/agent-design.md` 中的契约，包括 7 个工具、观察模型、等待、取消和目标复核。实现细节有变化时（文件工作线程、帧订阅），在批次 5 同步更新该文档中描述实现的句子。

## 9. 测量协议

三条路径分别测量，任何一条都不能代表按键到屏幕的总延迟：

| 路径 | 工具 | 基线（2026-11-19，本机） |
|---|---|---|
| 纯解析 + 网格（无 PTY、无历史） | `cargo run --release --locked --example bench` | 392.70 MiB/s（批次 0） |
| PTY `cat` 30 MiB → 解析，生产路径（磁盘历史） | 同上 | 137.20 MiB/s（批次 0） |
| PTY 回显 → 网格（无守护进程、无前端，磁盘历史） | 同上 | p50 9.02 µs，p95 10.37 µs，p99 12.46 µs（批次 0） |
| TUI 按键 → 回显（经本地守护进程，隔离 HOME 与运行目录） | `tools/latency.py tui` | p50 43.27 µs，p95 66.42 µs，p99 89.62 µs（批次 0） |
| 合成 Wayland 按键 → 呈现 | `tools/latency.py gui`，私有 headless Mutter 50.6 | p50 1.67 ms，p95 2.71 ms，p99 16.16 ms（批次 0） |
| 核心内存 | `examples/bench`（并入后） | 64 MiB 输出后 RSS 26.9 MB（无历史路径） |

规则：
- 在同一台空闲机器上用同一个 release 构建测量，每项重复 3 次，取中位数，与批次 0 比较。p50 或 p99 劣化超过 10% 时，回退该改动，或给出测量依据。
- TUI 回显基线的测法：子程序是一个原始模式小程序，只把读到的字节回写到 (1,1)。这样覆盖了“前端解码 → 套接字 → 守护进程 → PTY → 子进程 → PTY → 解析 → 取帧 → 前端绘制”的全链路。
- 生产路径基线的 CPU 剖析：`terminal-io` 线程是瓶颈，其中约 24% 的时间花在逐行 `malloc`/`free` 上；历史线程约 82% 繁忙，主要花在 `Archive::append` 的编码上。

## 10. 不采用的方案

- **通用异步运行时（tokio、smol 等）：** 关键循环只有几个到几十个 fd，`poll` 已经够用。执行器会增加调度层、`Send + 'static` 约束和大依赖，而磁盘、libcurl 和子进程等待仍然需要线程。
- **io_uring / epoll：** 每次唤醒只处理很少的 fd，重建 `pollfd` 数组的开销远小于一次进程唤醒。epoll 要维护额外的注册状态，io_uring 还会绑定内核版本。等窗格数过百、且测得 `poll` 成为热点时再议。
- **前端内嵌终端核心、取消守护进程：** 会失去分离与重连、多个查看端和 SSH 工作区。
- **保留每个窗格的 I/O 线程（现状），或像终端模拟器那样每个终端多个线程：** [Alacritty](https://github.com/alacritty/alacritty/blob/master/alacritty_terminal/src/event_loop.rs)、[Ghostty](https://github.com/ghostty-org/ghostty/blob/main/src/termio/Exec.zig) 和 [WezTerm](https://github.com/wezterm/wezterm/blob/main/mux/src/lib.rs) 都这样做，但它们要靠试锁、限制单次解析量、批间把锁交给渲染等手段控制等锁时间。[kitty](https://github.com/kovidgoyal/kitty/blob/master/kitty/child-monitor.c) 和 [foot](https://codeberg.org/dnkl/foot/issues/801) 说明单循环同样快。对已经有守护进程主循环的 nextty，单循环可以直接删掉这些锁及其交接机制（链接为 2026-11-19 的默认分支，引用前应固定到具体提交）。
- **刻意的输入或重绘延迟（kitty 的 `input_delay`/`repaint_delay`，foot 的 `delayed-render-*`）：** 这些延迟会直接计入回显延迟。kitty 去掉延迟后，实测延迟从 23.8 ms 降到 10.7 ms（[beuke.org](https://beuke.org/terminal-latency/)）。nextty 已用同步输出（模式 2026）加 150 ms 截止时间处理闪烁，不再加批处理延迟。
- **tmux 式慢客户端处理（未发送量超过每格 8 字节就丢弃并封锁客户端，之后全量重绘，见 [tmux tty.c](https://github.com/tmux/tmux/blob/master/tty.c)）：** nextty 的拉取模型让每个连接最多只有一个待处理的帧请求，慢客户端自然只收到最新状态，不需要丢弃和重绘机制。
- **替换系统库（HarfBuzz、FriBidi、Cairo/FreeType、Fontconfig、libcurl）：** 它们承担难写的工作，替换只会增加代码。
- **X11、其他合成器或平台兼容层；会话重启恢复：** 不在产品范围内。
- **为“现代”而引入 `rustix` 等系统调用封装：** `libc` 调用集中在少数文件里，封装不会减少逻辑，只会多一个依赖。
- **继续手写编解码：** 27 个函数、1,030 行成对维护，外加 740 行逐消息往返测试，字段顺序全靠人工保持一致。换成 derive 只多 1–2 s 冷构建时间。
- **bincode：** 2025 年停止开发，3.0.0 是故意无法编译的终止版本（[RUSTSEC-2025-0141](https://rustsec.org/advisories/RUSTSEC-2025-0141.html)）。
- **bitcode、wincode、rmp-serde、ciborium：** bitcode 的 serde 支持只是可选的次要接口；wincode 不走 serde，且要求 Rust 1.89；MessagePack 和 CBOR 是自描述格式，体积更大，而 ciborium 自 2024 年起没有发布新版本。
