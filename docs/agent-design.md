# Agent design

Nextty's agent completes tasks in the user's terminal workspace: inspect running programs and command results, read and change relevant files, execute work and verify the requested result. Keep one small model/tool loop. Its tools are `shell`, `input`, `read`, `open_terminal`, `read_file`, `search_files` and `edit_file`.

## Responsibility boundary

Nextty provides reliable terminal facts and convenient access to them. The agent chooses what to inspect, interprets the evidence and decides what to do next.

Nextty owns:

- Correct workspace/pane and filesystem-host targeting, existing shell state, input conflict checks and reads that preserve the user's viewport and selection.
- Command boundaries, exit status, and monotonic elapsed command time when shell integration supplies them; live screen state and retained history otherwise.
- Bounded terminal and file reads, literal search, continuation positions, asynchronous filesystem access, cancellation and explicit reporting of missing content.
- Faithful text extraction, physical row coordinates, wrapping and cursor visibility. Keep presentation cleanup conservative and independent of application names.

The agent owns:

- Choosing panes, files, command output, history or the live screen, and selecting the relevant range or query.
- Deciding whether to continue reading, wait, interact or broaden the evidence.
- Application commands, file changes, debugger configuration, task relevance, diagnosis and verification of the user's objective.

Do not infer task relevance from keywords, recognize applications to select a hidden policy, summarize evidence before the agent sees it, or treat a quiet interval as application readiness. Report unknown state as unknown. Queued input, screen activity and an elapsed wait are not proof of completion.

## Observation model

Terminal evidence uses two data shapes, without application-specific adapters:

- **Text:** a bounded part of one command's output or the main terminal's retained text, with a continuation cursor, `has_more` and `incomplete`. Include command execution state only for command reads.
- **Screen:** the live application's rows, original coordinates, size, wrapping and cursor visibility, with the current input/foreground state needed to operate it. Full session identity belongs in the initial context, not every read.

Prefer command output for shell tasks. Ordinary debugger commands can also be inspected as newly appended text. Use a screen snapshot for interfaces that overwrite their layout. An executable name or alternate-screen flag alone does not determine which observation the task needs.

## Reading and continuation

- Keep a usable `cursor` at the end of the available text. `has_more` means this snapshot still contains unread text; it does not mean the program is running. `incomplete` means retained evidence is missing.
- A cursor belongs to one pane, source and command. Its offset is a UTF-8 byte position in that source's rendered physical row, not a terminal column. Resize/reflow or clearing can invalidate it explicitly.
- Preserve appends to an unfinished final row, later hard newlines and soft wraps. Do not advance over unused blank screen rows.
- History is retained rendered terminal text, not an immutable recording of PTY bytes. Use screen observations for overwritten content; do not promise that a text cursor detects edits to previously read text.
- A literal query searches forward from the supplied cursor, or the retained range's beginning when omitted, and selects a bounded excerpt around the first match. Text search can return one contiguous excerpt per read; the cursor continues after the inspected excerpt and does not identify the match's coordinates. A query is range search, not a persistent streaming matcher across requests.
- Preserve literal matches across physical wrapping and archive boundaries within a read. Keep UTF-8 boundaries and report clipping or missing evidence honestly.
- The agent controls whether to retrieve more context. Defaults must be bounded and predictable; do not automatically return only lines classified as errors or important.

## Screen presentation

Extract the current screen from terminal cells, independently of the user's scroll position. Preserve substantive text, titles, addresses, instructions, pointer chains, change markers and layout. Omit only clearly defined empty or decorative rows; do not grow a catalog of application-specific cleanup rules.

A query focuses on matching rows and neighboring context while retaining the visible input row. An unfiltered screen read remains available. Keep snapshots stateless; add screen differences only if measured benefit justifies baseline, deletion, resize and rewind handling.

## Harness and implementation

Screen frames use one pull path for local and remote frontends and the Agent owner. A frontend keeps its next frame request pending; the owner requests frames only for pending work. Tool execution obtains a fresh snapshot before interpreting or acting on terminal state. Every forced refresh gets a new request identity, including when another forced refresh is pending, so an older in-flight frame cannot satisfy a later observation.

Tools within one conversation execute in order. Input authorization and observed activity are tracked separately for each pane; reading another pane does not discard an earlier observation, and the daemon still rejects input after intervening user changes. Conversation updates carry ordered message patches; preserve their order and intervening lifecycle events. Consecutive queued draft snapshots may be replaced by the latest draft before presentation. The frontend publishes drafts only when their content changes; do not retain a second JSON copy merely to compare it with that dirty state. Network activity, terminal/history waits and presentation work must not block frontend input. Record known tool results before fallible UI notifications. Keep input authorization separate from the activity observation used for waits.

Waits are bounded observations. Waiting for a fresh screen cannot suspend an active observation deadline; if the frame is still unavailable at expiry, report an observation error and retain any confirmed input or terminal-creation facts. `read.wait` is an integer number of seconds, from 0 through 1800; omission or 0 reads immediately. Return a reason and current state so the agent can continue or respond to an interactive prompt; do not wake the model for every output line. Stopping the agent cancels its own requests and waits, not programs already running in the terminal. Preserve results already received when cancellation arrives, then stop before another action or model request.

An interrupted or failed request does not establish that its terminal action never happened. The agent must inspect current state before repeating an action; the harness must not automatically replay PTY input after an uncertain outcome.

Model HTTP requests use a 15-second connection timeout and a 600-second low-speed window below 1 byte per second, allowing quiet model reasoning or gateway queues while remaining cancellable. Transient model transport failures, truncated SSE streams, HTTP 408/429/500/502/503/504/529 and streamed API/overload errors retry the same model request up to three times, waiting 1, 2 and 4 seconds. The wait is cancellable and never blocks frontend input. Execution, summary and goal-review requests share this path. Discard an incomplete model response and its displayed draft before regeneration; retain all earlier complete tool exchanges. Tools execute only after the entire model response completes, so regenerating that response cannot replay an already executed tool. A valid completed response ending in `message_stop` returns without waiting for HTTP framing to finish. Consume any already completed libcurl transfer before detaching so normal connections remain reusable; an unfinished HTTP/1.1 connection is closed rather than drained in the background. Authentication, malformed payloads, local limits and other permanent errors surface immediately; exhausted retries preserve known results and report the final error. This retries model generation, never an uncertain terminal or file action.

Once a shell submission is acknowledged, retain `input_queued` and its command ID even if the following observation fails, returning `observation_error` instead of discarding these facts. This also applies when an accepted shell or input operation's observation exceeds the 64 KiB tool-result limit: return the acceptance facts and an explicit observation error so the agent can choose a focused read without replaying input. Do not silently clip a live screen. A command can clear its own retained output; missing output is not evidence that the command never ran. Standalone reads still report unavailable evidence as an error.

After accepted `input`, observe for up to 100 milliseconds for a change to the live screen's text, cursor, geometry or retained extent, and return a fresh screen with `input_queued` and `outcome` (`changed` or `timeout`). Track screen activity separately from input generation and command metadata so the acknowledgement itself cannot finish this observation. This combines sending and bounded observation without classifying the foreground application or inferring readiness. The agent decides whether the returned evidence is sufficient or another read is needed. Cancellation or an observation failure preserves the accepted-input fact and reports `observation_error`; it must not turn a successful submission into a claim that nothing happened.

Use plain data and existing modules. Avoid compatibility aliases, tool registries, automatic application modes, new services or parallel writers to the same PTY. Validate changes on real shell/PTY paths and representative debugger screens. Measure data correctness and local overhead separately from real-model task quality. The bounded presentation transcript trims oversized replies in chunks, leaving room for later deltas so each small append does not force a full model patch and layout reset. This does not change the harness conversation or its compaction policy.

## Workspace and native files

A submission includes the target pane's live screen and a compact workspace inventory. `read` with `source: "workspace"` refreshes that inventory across every tab. Each pane reports its actual tab, directory, foreground facts, prompt and recent command metadata. Terminal and file tools require an explicit pane ID; the agent chooses it. Agent observations and input must not reset the frontend's focus, scroll position or selection. Program output can still change terminal content normally.

`shell` requires a non-null `shell_prompt` in the pane's latest observation and an untouched integrated prompt at execution. `input` interacts with the current foreground program; it is not an alternative way to run independent shell commands in an occupied pane. For independent commands, reuse a suitable terminal the agent already opened, or use `open_terminal` and its returned new pane ID. Its argument identifies the source directory context, not the target for subsequent commands. Native file tools use the selected pane only for filesystem context and work while its foreground program is occupied. `read_file` reads one regular UTF-8 file; directory listing belongs to shell tools. `search_files` searches file contents, not filenames.

`open_terminal` creates one visible, unfocused tab in the source pane's current directory and returns its exact pane ID with a fresh screen observation. It starts the workspace's default shell, without copying another shell's runtime environment, functions or jobs. After acknowledgement, reuse the frame/event path to observe for up to one second for an integrated shell prompt. The returned observation records the pane's input generation and may authorize the next command without a separate `read`. A timeout returns the actual screen and prompt state; it does not establish readiness. Observation failure, cancellation or an oversized screen preserves `created: true` and the pane ID with `observation_error`. This allows work and verification while an existing CLI agent, debugger or other program retains its foreground PTY. Creation is an explicit model action, not a per-task default; reuse a suitable created terminal rather than accumulating tabs. Native file work needs no PTY. Keep independent executable work in an inspectable workspace terminal; a hidden one-shot shell would add another process lifetime and observation path without inheriting the user's shell state. A missing acknowledgement is an uncertain result, not permission to repeat creation.

Native file operations run on the workspace daemon's host, through the existing local or SSH protocol. Relative paths resolve once against the selected pane's directory before queueing; absolute paths remain on that same host. A foreground `ssh` program inside a local pane does not change filesystem authority. The agent uses terminal interaction when intentionally operating through such a program; nextty does not infer a different filesystem from application names.

- `read_file` returns exact UTF-8 text, at most 16 KiB, with byte `offset`, `next_offset` and `has_more`. Preserve CR, tabs and all substantive content. Offsets refer to current contents, not an immutable version of the file.
- `search_files` searches a selected file or directory for literal text in UTF-8 regular files, without an index, regex mode or application policy. Results include file paths, 1-based line numbers and excerpts, bounded to 100 matches and 16 KiB of excerpt text. Binary/non-UTF-8 files and symlink directories are skipped; files over 8 MiB and clipped/capped results set `truncated`. The agent narrows the path/query or uses shell tools when it needs broader evidence.
- `edit_file` replaces exactly one occurrence of `old_text` in a current UTF-8 file up to 8 MiB, preserving unrelated content. `old_text: null` creates a new file without overwriting an existing one; its parent must exist. Existing edits follow symlinks to their targets and preserve file permissions. Stage content in the same directory, check content and file identity for intervening changes, then commit without exposing partial text. This is optimistic conflict detection, not atomic compare-and-swap against arbitrary editors or a crash-durability guarantee.

File work bypasses screen refreshes and runs on one lazily created worker per owner connection. Its FIFO retains every conversation's request; submit the next job only after consuming the current result because the reusable worker has replace-latest slots. Neither file traversal nor file writes run in the daemon input loop. File access requires the authenticated Agent owner, independently of ordinary frontend attach/control rights. Pane closure, PTY exit and owner disconnect cancel owned work without joining filesystem I/O on an input thread.

The file worker records successful `edit_file` operations for frontend review using the exact before/after content already held during the write. Records carry per-operation added/removed line counts and a bounded unified diff; the owner associates them with the conversation turn. Each record retains its exact tool-call display identity so the frontend can show it beside that tool’s history entry. Frontends group records by path in a collapsible summary and expose a centered read-only diff viewer. Counts are cumulative edit-operation counts, not net Git changes, and shell/editor changes are not attributed to the agent. Keep diff payloads out of model tool results. Retain at most 1,024 records and 256 KiB of diff text per conversation, mark truncation and omitted records, and preserve actual edit records across conversation rewind. The owner advances the existing model revision whenever file records change. Patches include the full record list on first publication and after a revision change; omitting the list retains the previous records, while an explicit empty list clears them. The daemon keeps a complete record snapshot for new frontends and reconnects. Within each process, snapshots share the record list; the owner uses copy on write when recording another edit.

Cancellation is checked during file work and before committing a write. Once committed, return `written: true`; preserve received results before cancellation and presentation errors. An interrupted request without a result may already have acted, so inspect current files before repeating it. Stopping the agent leaves its visible terminals and their programs available to the user. Planning, diagnosis, choosing another CLI agent and deciding whether verification meets the user goal remain model responsibilities; no second scheduler or application-specific adapter is needed.

## Conditional monitoring

Keep conditional monitoring in the existing conversation and PTY. The agent chooses a command that finishes when the requested condition holds, then uses a command read with an appropriate wait, for example `{"pane":7,"source":"command","command":123,"wait":300}`. The owner sleeps until command completion or the observation deadline while the frontend and other conversations continue working. One pending read needs no additional nextty watcher process, task registry or model polling loop.

The condition belongs to the command or to the agent's interpretation of its output. A build can report its own exit status; a log-watching command can exit on a selected event. The agent is responsible for bounding and cleaning up processes it explicitly starts. A read timeout only ends observation. Screen/history waits still return on terminal activity, and a query still selects an excerpt; it is not a persistent streaming predicate. Choose short waits when an interactive prompt may need attention. A successful condition command is evidence about that condition, not proof of the user's whole objective.

An outstanding read occupies that conversation's tool loop. Stopping the conversation cancels the wait promptly; an already running terminal command remains available for explicit interaction. Continued operation after a frontend detaches follows the existing owner lifetime; restart recovery is a separate product requirement.

## Context, goals and orchestration

Keep the model/tool loop distinct from goal completion. The harness executes requested tools, appends their results and asks the model again. Every user submission is a goal by default. A final model response triggers a private, tool-disabled review of the active request and available evidence using the same model and conversation worker. A `continue` decision identifies unfinished work and feeds it into the existing loop; `complete` ends the goal, and `blocked` ends the run with the missing prerequisite visible to the user. Ordinary questions can complete with an adequate answer and do not require terminal actions. The review is a model assessment, not independent proof of success. A blocked review emits an explicit blocked conversation event, distinct from a continuation notice. The tab status dot uses orange while the agent is busy, red for a settled turn with an error or blocked event, and green otherwise; tool errors during continued execution do not end the running state.

There is no goal-wide token, model-call, iteration or elapsed-time budget. Existing per-request output limits, context compaction, bounded reads and transport timeouts still apply. User stop, rewind and conversation shutdown cancel execution and reviews through the same cancellation path. A failed or malformed review surfaces an error and preserves known results; it does not report completion or automatically retry terminal actions. A review must consider actual progress and report a genuine blocker when no useful action remains. It cannot expand the user's scope. Goal state follows the existing owner lifetime across frontend detaches, with no restart persistence, new process or task registry.

Loop engineering supplies objective, verification and stopping policy around the model/tool cycle. Graph engineering makes dependencies and verification-gated transitions explicit for a known workflow. Neither requires a graph execution framework for an interactive terminal assistant.

Current choices:

- **Retrieval:** keep command IDs, paths, literal queries and cursors as references and fetch evidence when needed. Shell search and terminal history are the first retrieval mechanisms. Add semantic RAG only for an identified corpus where text search demonstrably misses useful evidence; account for index freshness, provenance and retrieval cost.
- **Prompt cost:** describe shared read semantics once rather than repeating them in every schema branch. Keep tool definitions and earlier messages stable between requests. Execution requests opt into automatic prefix caching with `cache_control: {"type":"ephemeral"}`; gateways must support this Messages API field. Summary and goal-review requests do not request cache writes. Each final model response normally adds one goal-review request. Cache hits reduce repeated processing, not context length, and must be measured from provider usage rather than assumed.
- **Context:** keep recent complete tool exchanges and the original active request while summarizing older work. A final answer or goal-review prompt does not replace the latest tool exchange: retain its call and original result in the review context, and summarize earlier material. Summaries are fallible historical context, not current terminal facts or a complete session recording. The byte budget bounds local serialization; it is not a model token-window measurement.
- **Monitoring:** wait on a concrete execution event without repeated model calls. Keep semantic conditions and decisions in the agent; keep deterministic execution state in nextty.
- **Subagents:** introduce them only for independently useful work with isolated context and measurable benefit. A future read-only analysis of a frozen log could qualify. All actions on a shared PTY must still pass through one ordered writer and current input authorization.
- **Goals:** continuation and evidence review are the default for every submission, without an enabling command or configuration mode. Preserve the active user request and completed tool results across reviews and compaction. No automatic budget cap is imposed, as requested by the user. A generic reminder to continue is insufficient: reviews must identify concrete missing work or the prerequisite preventing progress.

Use the existing owner process for workspace coordination, one lazily started worker per conversation for model I/O and context, and existing history workers for searches. Add concurrency where independent work can proceed; avoid adding workers to a dependency chain. Measure model-request count and evidence correctness as well as local CPU and input latency.

## Evidence behind these choices

Reviewed against public sources on 2026-11-03. Product features, research results and practitioner reports inform these choices; they do not establish nextty's task quality. Prefer fixed source revisions and original experiments. Treat third-party leak analyses as unverified claims; use public documentation or code to substantiate a mechanism.

- **Small loop and facts:** OpenAI's [Codex loop](https://openai.com/index/unrolling-the-codex-agent-loop/) (2026-01-23) and [public execution handler](https://github.com/openai/codex/blob/451787127c0e70247034c33e358536ffd2b89cf8/codex-rs/core/src/tools/handlers/unified_exec.rs) (2026-11-02 snapshot), and [Claude Code's documented loop](https://code.claude.com/docs/en/how-claude-code-works), separate model decisions from tool execution and feedback. Their owned subprocesses differ from nextty's shared PTY; do not copy termination or control policies blindly.
- **Useful bounded results:** Anthropic's [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11) and [Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) (2025-09-29) support lightweight references, just-in-time retrieval and task-based evaluation. DeepSeek's [terminal tools](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/experimental/tool-terminal/README.md) (2026-10-29 snapshot) return bounded startup/send output and prefer one-shot file/shell tools for bounded work, reserving persistent terminals for cross-call state or interactive input. They do not expose a TUI/key-sequence/resize surface or compare visible tabs with hidden shells. Nextty combines accepted input or terminal creation with observation to avoid a mandatory blind read; silence, a timeout or creation itself still cannot establish readiness.
- **Edit format:** The [hashline report](https://stencil.so/blog/the-harness-problem) distinguishes gains over patch from gains over exact replacement; its current revision differs from the original experiments. The [2026-02-12 implementation](https://github.com/can1357/oh-my-pi/blob/7a6b42353eab3e412d14902ac26cdae9934e149e/packages/coding-agent/src/patch/hashline.ts) hashes whitespace-stripped lines into eight bits and validates range endpoints, so it does not establish that the entire replaced range is unchanged. Keep one unique exact replacement protocol. A stricter hashline candidate must account for read annotations, version checks, paging and rereads as well as shorter edit arguments; measure the complete loop before replacing the current tool.
- **Event waiting and recovery:** DeepSeek's [Super-agent execution](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md) and [architecture](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/007-architecture.md) (2026-10-31 snapshot) separate background work, worker readiness and external completion, and inspect current state on recovery. The [README](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/README.md) identifies research code, not an official product or the complete internal implementation. Borrow event-driven continuation and bounded original evidence; its ticket, subscription, outbox and persistent intake services address a different lifecycle. Stopping a nextty observation leaves the user's program running. Its [attention-cost principle](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/000-philosophy.md) supports minimizing tab creation and focus changes; choosing visible, reusable terminals is a nextty design judgment, not a measured outcome of that prototype.
- **Action boundaries and retrieval:** [pi's loop](https://github.com/earendil-works/pi/blob/48f9f1b423bea5275c96274f3442a805e0c57c17/packages/agent/src/agent-loop.ts) and [Hermes history search](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/tools/session_search_tool.py) (2026-11-02 snapshots) provide examples of steering at tool boundaries and on-demand source retrieval. Current Hermes search truncates message content explicitly; older claims of unlimited original retrieval are stale. Neither product justifies adding another scheduler or memory database to nextty.
- **Loop versus graph:** Addy Osmani's [Loop Engineering](https://addyosmani.com/blog/loop-engineering/) (2026-06-07) is practitioner guidance about discovery, triggering, recorded progress and verification. The [loop adoption study](https://arxiv.org/abs/2608.21884v3) (2026-10-22 revision) identifies missing systematic evidence for broad benefit claims. [Graph Engineering](https://arxiv.org/abs/2608.21156v2) (2026-08-26 revision) proposes explicit task/agent/state structures. [Cloud engineering](https://arxiv.org/abs/2609.00050v2) (2026-10-16 revision) applies graph gates to predefined deployment predicates. These are not evidence that general terminal assistance needs a graph engine.
- **Remove scaffolding when evidence permits:** Anthropic's [long-running harness design](https://www.anthropic.com/research/harness-design-long-running-apps) (2026-03-24) and [Managed Agents](https://www.anthropic.com/research/managed-agents) (2026-04-08) describe removing context resets and repeated evaluation phases as models improve. Nextty's goal review is a stopping-policy assessment, not independent proof. Measure false completion and actual outcomes before adding or removing reviewers.
- **Context and cache limits:** [The Complexity Trap](https://arxiv.org/html/2508.21433v3) (2025-10-27) finds simple observation masking competitive with summaries in its experiments; [Demystifying Harness Effects](https://arxiv.org/html/2609.32459v1) (2026-09-26) reports task-dependent compression tradeoffs. These make masking a candidate for paired evaluation, not permission to discard terminal evidence silently. Anthropic's [cache rules](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache) state that changing `system` invalidates downstream caches and changing `tool_choice` invalidates message caches. Reusing only the execution system prompt would not guarantee full-history cache reuse during tool-disabled goal review.

Evaluate changes with the same model, tasks, initial state and verification criteria. Record actual task outcomes, unsupported success claims, tool/model requests, elapsed time and provider input/output/cache usage separately. Context-policy changes also need long-output diagnosis, interactive prompts, overwritten screens and compaction-spanning tasks. Local SSE fixtures prove routing, cancellation and overhead; they cannot prove real-model task quality, token savings or cache hits. `tools/agent_eval.py` exercises occupied-pane file repair and long-output interactive execution with a real model in private workspaces, recording provider usage without adding telemetry state to the product loop. Independent filesystem/process checks establish outcomes beyond model self-report. A few successful tasks establish feasibility, not a statistical error-rate improvement.
